* Stage 1: Bedrock Starting Point

Goal: Turn the copy of bisos.airflow into the PostgreSQL bedrock capability of BISOS, and
settle the layering that bisos.airflow (and later django-based packages) will consume.

** Decisions Taken (discussion of 2026-10-03, started in bisos.airflow TODO 4.3.1)

- PostgreSQL is *BISOS's sole database*. Other packages (django, ...) converge on it.
- It is a generic *bedrock* layer on which other capabilities are built. In the BISOS model
  many capabilities co-exist consistently, on multi-tenant VMs (not on containers).
- A bisos-pip package =bisos.postgres= with its own CBS (=postgres-cbs.pcs=) and a CBM leaf at
  =sys/cbm/collective/bedrock/postgres/=: a new capabilityType =bedrock= under the
  =collective= realm.
- *The CBM walker processes the bedrock capabilityType first.* So no CBS invokes another
  CBS. Airflow's sbom should still cheaply assert that the cluster is up, because a walk of
  the airflow leaf alone would skip bedrock.
- *No systemd unit is authored.* Debian's =postgresql.service= is used as is. Tenants' units
  say =Requires=/=After= =postgresql.service=. (=postgres-sysd.pcs= was deleted from the copy.)
- *No assemble step*: no .here fqdn and no web vhost. =postgres-assemble.cs= was deleted too.
- =max_connections= baseline of *200 or more* is owned by the bedrock layer, not by a consumer.
- Tenant model: a role plus a same-named database owned by it, reached by *peer
  authentication* from the like-named OS account over the unix socket, no password anywhere.
  The administrator is the =postgres= OS account that Debian creates; only bedrock uses it.
- =libpq-dev= (client headers) lives in the bedrock sbom. The pip drivers (=psycopg2=,
  =asyncpg=) stay in each consumer's sbom, because they install into the consumer's virtenv.
  (Recommended in discussion; Mohsen asked what else uses them but has not yet confirmed.)
- Candidate tenants beyond airflow and django: Nextcloud, GitLab, Gitea/Forgejo, Matrix
  Synapse, Grafana, and others. None of them exists in bisos-pip yet; nothing else in
  bisos-pip mentions psycopg or postgres.

- *The BISOS Platform is edge-oriented and includes a desktop* (Gnome or a thin one); ordinary
  users manage their own platform. A GUI on a BISOS host is a given. (Recorded in the bisos-pip
  =AI-Activity.org= template, Core Vocabulary, 2026-10-03.)
- *Clients are layered, not a single tool*: =psql= (the baseline, in every bedrock install), Emacs
  (=sql-mode=, org-babel SQL, PGmacs) for Blee, DBeaver Community Edition as the optional GUI, and
  Microsoft's PostgreSQL extension for VS Code. VS Code is an accommodation for proprietary
  environments; Blee is the Libre-Halaal answer. SQLTools was considered and not chosen.
- *=dbeaver-sbom.pcs= lives in =bisos.postgres=, as a file separate from =postgres-sbom.pcs=, and is
  part of the =bedrock= capability* (not =induct=). It is pulled in through =sbomsList= (option (a);
  the alternative, its own =bedrock/dbeaver= leaf and CBS, was not chosen). *Refined 2026-10-03*: a
  group sbom, =dbClients-sbom.pcs=, sits between them: =postgres-sbom.pcs= pulls in
  =dbClients-sbom.pcs=, which installs =postgresql-client= and pulls in =dbeaver-sbom.pcs=. Reasons:
  precedent (=ai-tools-sbom.pcs= is a group that pulls in a sub-sbom); a user's edge platform may need only
  the clients, to reach a cluster on another host, so the group stands alone, without the server; and
  =dbeaver-sbom.pcs= stays a file of its own for vendor-source isolation (as =vscode-sbom.pcs= keeps its
  vendor source). Sub-sbom specs are named by the path of the file's own directory, not by bare name:
  =ai-tools-sbom.pcs= names its sub-sbom by absolute path, and a bare name needs the package on PATH. Mechanics, read in =bisos.sbom=:
  =sbom_fullUpdate= does apt, pip and pipx first and then =sbomSpecs_fullUpdate all=, so the server
  is already installed when the DBeaver sbom runs; =AptPkg= has only name, func and osVers, so a
  vendor package source needs a func-bearing pseudo-package like =postgresClusterSetup=.

** Tried And Rejected

- Authoring our own =postgres-sysd.pcs=: it would duplicate and fight Debian's units.
  (It was in the airflow copy only by accident.)
- Putting DBeaver in =postgres-sbom.pcs= itself: kept separate for failure isolation from the
  cluster-restart logic and for third-party package trust. (Claude's argument that servers are
  headless was withdrawn: it is wrong for the BISOS Platform.)

** TODO [#A] <<1.2>> Decide the interface for a tenant to ask for its role and database :aiAndMe:
SCHEDULED: <2026-10-03 Sat>
Today airflow does this itself (=airflowPostgresSetup= in its sbom: =CREATE ROLE=, =createdb=).
Bedrock should own the commands; a consumer should only declare "role X, database X, owner X".
Two forms:
 - (a) a Python function in =bisos.postgres=, e.g. =postgres.ensureTenant("airflow")=, called
   from the consumer's sbom. Simple and explicit; ordering matters.
 - (b) a declarative entry in the consumer's sbom, in the style of =ap(...)= / =pp(...)=. Fits
   the sbom idiom, but =bisos.sbom='s =pkgsSeed= may only express apt and pip.
Read =bisos.sbom= (=pkgsSeed.py=, =sbom_csu.py=) first, then recommend. Whatever the form it
must be idempotent, and must not recreate an existing role or database.
