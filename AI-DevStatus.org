* Key Design Decisions

  - *Sole database; bedrock layer.* Other packages converge on it. Tenants are a role plus a
    same-named database, reached by peer authentication from the like-named OS account: no
    secret anywhere. Only bedrock uses the =postgres= administrator account.
  - *No authored systemd unit, no assemble step.* Debian's unit is used; there is no .here
    fqdn or vhost. =postgres-sysd.pcs= and =postgres-assemble.cs= were deleted.
  - *Walker order, not CBS-to-CBS invocation.* The CBM walker does the =bedrock=
    capabilityType first, under the =collective= realm.
  - *=max_connections= >= 200 is bedrock's baseline*, since it is server-wide.
  - *=libpq-dev= here; pip drivers with consumers* (provisional: see Stage 1 decisions).
  - *Clients are layered*: =psql=, Emacs (=sql-mode=, org-babel, PGmacs), DBeaver CE as the
    optional GUI, Microsoft's PostgreSQL extension for VS Code (proprietary environments only).
    The BISOS Platform is edge-oriented and includes a desktop, so a GUI on a host is normal.
  - *The clients are a group*: =postgres-sbom.pcs= pulls in =dbClients-sbom.pcs= (apt
    =postgresql-client=; stands alone, for hosts with no local server), which pulls in
    =dbeaver-sbom.pcs= (the vendor apt source and =dbeaver-ce=; a file of its own for failure
    isolation). All three are part of the =bedrock= capability (written 2026-10-03, TODO 1.9; not
    run). Sub-sbom specs are named by the path of the file's own directory, so none needs the package
    installed or on PATH. The DBeaver vendor key is trusted on first use. DBeaver CE sends anonymous
    usage statistics by default; it is switched off per user.
  - Open: whether the VS Code extension can use the unix socket with peer auth (1.10).
  - *=postgresClusterSetup= is a func-bearing pseudo-package* run on every =sbom_fullUpdate=,
    so it must stay idempotent and its position after =postgresql= in =aptPkgsList= is load-bearing.
  - Tried and rejected: our own =postgres-sysd.pcs= (duplicates Debian's units).
  - Always reference repos via =/bisos/git/bxRepos/...= (see =AI-Activity.org=).

* BISOS Vocabulary (formalized 2026-10-03)

  The terms were corrected by Mohsen and written into the terminology panel and the =bisos-pip=
  =AI-Activity.org= template (pointers below). In short: *BISOS-Platform* is the general concept;
  *BISOS-System* is *this particular* platform (what =sys/= denotes); a *BISOS-Compatible-OS* is an
  OS BISOS can be loaded onto (all Debian: Debian, ChromeOsDeb, Termux); a *BISOS-Compatible-Box* is
  a Box plus one; a *Raw-Platform* (RAW-BISOS) is a stage: a compatible Box from a Fresh-Debian with
  BISOS loaded, not yet sited. The BISOS Platform is edge-oriented and includes a desktop, so GUI
  software on a host is normal (do not object to it on "servers are headless" grounds). Check BISOS
  terms against the panel and ask when unsure.
